# Security model — DSH MCP Console

For a potential vulnerability, do not publish exploit details, credentials, profile configuration or private logs. Use GitHub private vulnerability reporting if enabled; otherwise request a private contact channel through a sanitized issue. This document describes design boundaries, not a security certification.

## Scope and authority

This console owns one per-profile store and only the official MCP-client children it creates. It never imports/migrates existing credentials or changes native MCP/SAP/profile configuration. Public `profileContext` path metadata selects separate private storage; no profile configuration contents are read.

Management uses the existing authenticated Typert carrier. Gateway/RemoteAccess plus an invocation-owner guard protect every RPC before queuing or IO. Requests/results are strict/bounded. Management RPCs are **not model-facing tools**. Connections/tools belong to the active **profile**, potentially shared by its chats; host execution/governance remains unchanged.

The explicit `saveAndActivate` request contains the current revision, exact server metadata and `SAVE AND ACTIVATE THIS SERVER`. User-visible Save authorizes execution of that stdio command or contact with that URL, initial handshake/tool synchronization, retention of the verified connection and enabled intent for future profile startup. The compatibility `save` endpoint stays metadata-only and cannot enable an unvalidated target; the UI never uses it as a fallback. The controlled Switch authorizes the unchanged exact Start/Stop requests and saves enabled/disabled preference. With `capabilities.persistentActivation:true`, checked state follows the persisted per-row preference, separately from qualified connection status. Absent capability preserves the old UI behavior. No automatic business-tool invocation, continuous reconnect loop or non-invasive probe is added.

Authentication is not transport encryption. Tokens/passphrases are JSON over the page's existing RPC carrier. Android uses loopback HTTP; access from another device needs HTTPS/an encrypted tunnel. A login cookie or plain-HTTP proxy alone does not provide confidentiality.

## At-rest vault and write-only fields

AES-256-GCM uses versioned authenticated data, random 12-byte nonce and 16-byte tag. Automatic production stores use a random 32-byte key in a separate regular 0600 file under this plugin's 0700 directory. The `app-private-key-v1` envelope has distinct authenticated domain/salt. Key IO refuses symlinks/unsafe ownership, permissions, type, length and links, and creation is serialized under the writer lock. Initialization occurs only on an authenticated revision-valid credential write. Opening/refreshing creates no key/files/server. Credential-free verified Save connects and creates metadata only after success, not a key/envelope. Missing/corrupt keys for an existing envelope fail closed and are not regenerated. Interrupted first publication may leave a reusable orphan key; no ambiguous deletion is attempted.

Existing scrypt envelopes remain manual without automatic conversion. Fixed `N=32768,r=8,p=1` derives a key from a 12–512-character passphrase, not persisted with ciphertext. Manual startup is locked; unlock is explicit/temporary (30–900 seconds, five minutes in UI). Three failed unlocks impose a 30-second in-process delay. Automatic private-key rehydration at startup is permitted only for an explicitly enabled saved record and never creates/replaces a missing key; automatic Lock/initialize/unlock are not a revocation API.

The API never returns stored secret values or file keys. Snapshots contain only mode, opaque ref names, metadata, feature capability and qualified status. Masked uncontrolled DOM inputs clear before credential submissions and on relevant context departure. Repeated initially locked manual polls preserve typing, but actual lock/expiry clears it. Automatic `expiresAt:0` is not expiry. No browser local/session storage or own diagnostics hold secrets. During sequential writes, remaining new values briefly exist in local JavaScript variables and clear at handoff/finally; string zeroization is not promised.

This is **not Android Keystore**, hardware/biometric protection or recovery. Root, same-UID/same-process code, or a backup containing key+ciphertext can recover credentials. Private files exclude ordinary other-app access. Losing the key/manual passphrase loses access; weak manual passwords allow offline guessing. JS/SDK/environment/browser/process/server copies cannot all be wiped. Byte buffers are wiped where possible. Encryption does not protect against an authorized server echoing credentials or compromised owner/same-process plugins.

## Simple HTTP Token and Headers

Optional Token formats a new value as Authorization Bearer. Full exact Authorization (including its prefix) belongs in header Value with Token empty. New Token + new Authorization is rejected before writes. Token can replace an existing blank Authorization binding; unrelated custom headers remain unless explicitly trashed. There are no ref-name/keep/replace/clear controls in normal HTTP use. Scoped stdio/legacy advanced credential editors remain write-only.

Stable uncontrolled password inputs/row refs hold typed values, not React state/storage/logs. New values use fresh 128-bit cryptographically random refs; never overwrite an old shared secret. Complete metadata/value/count/collision preflight precedes writes. Secure-random/key failure, expired manual vaults, a mounted edited target, duplicate/control headers and renamed blank opaque bindings fail closed. With other owned mounts, fresh-ref writes require automatic mode and explicit `appendSecretsWhileMounted:true`; an old/missing-capability host and the advanced existing-ref editor retain the global mounted guard. The small target-disabled helper changes explanation only, not the Edit Config layout or native styles. HTTP values are bounded against line/control injection.

A host lacking `capabilities.saveAndActivate:true` cannot accept the new flow: UI displays a fixed reload notice and retains typed masked inputs without secret/network writes or DOM collection. There is no silent fallback to unvalidated Save or password setup. Updating the frontend/page alone does not prove host-generation reload. Context departure/reload still clears transient input under the existing safety policy.

Each `setSecret` advances the revision, then `saveAndActivate` connects/verifies/persists bindings and retains that owned connection. This credential+configuration sequence is **not atomic**. An uncertain response stops subsequent writes. Pending UI contains only refs/status/metadata/revisions. Explicit retry reads a fresh snapshot, reconciles exact config and verifies its active state/timestamp before treating an ambiguous response as success. It must not blindly activate again or label an inactive/unverified match successful. Missing values need explicit reentry with different refs. Unused encrypted values may remain after failed/abandoned validation; no speculative value deletion occurs. Only an authenticated definite initial `mount-failed` permits releasing the Save-pending marker and fully confirmed active credential-write markers while retaining bindings/revision, so the user can correct an invalid URL/token. Ambiguous transport, publication and cleanup errors never use that release; no secret is restored to DOM or old value overwritten.

Empty new Token/headers add no binding/Authorization or key. Blank existing values preserve opaque bindings; renamed saved headers need reentry. Header trash removes a binding on successful Save, not encrypted value/provider token. Deleting a server similarly does not auto-delete credentials or revoke provider tokens. Provider authentication discovery/OAuth is unsupported.

## Append-only credentials while other mounts remain

Only automatic mode advertises optional literal-true `capabilities.appendSecretsWhileMounted`, and mounted unknown-authentication/quarantine states withhold it. The backend independently enforces the append-only rule; a client flag is not authorization. Authenticated envelope/ref metadata is retained separately from wipeable key/plaintext cache, so cache loss cannot turn an existing ref into a permitted new one. Known overwrites/deletes and capacity/revision/owner failures remain pre-key-IO denials. The unchanged protected private key reauthenticates current ciphertext before sealing a fresh alias. An empty-vault exception applies only to genuine first credentials with credential-free owned mounts, never disappearance of an authenticated vault. Mounted handles, resolved upstream credentials and verification timestamps are not modified by append.

Mounted append validates its result before publication. Definite prepublication write failure preserves the previous state; uncertain/read-back/publication or lock-release failure is not assumed success and is not automatically undone. `secret-state-ambiguous` quarantines credential access while preserving live owned handles, and withholds append capability. A confirmed attempted ciphertext may be reconciled by snapshot without enabling further append. Unrelated/unreadable state retains drift evidence rather than adopting changed secrets. Resolve the writer-lock problem and reload only this plugin/fresh controller to recover; this error does not silently stop/reconnect servers or restart the engine. Reload itself can dispose this plugin's connections, so subsequent activation remains explicit. If an authenticated automatic vault is removed or its KDF/ciphertext changes while mounted, an explicit Stop can clean only its requested owned target and then report `vault-drift` without a store write or sibling teardown; corrupted mode metadata cannot trigger manual global TTL/Lock cleanup.

## Exact tool policies, timeout and safe failure categories

The new owner-only `setToolPolicy` is revision/ownership checked. Exact public names must belong to that saved server namespace, be unique ASCII identifiers of at most 64 characters, and number at most 512. No raw-name reversal, provider descriptions/schemas or namespace editing is added. Include-empty is intentional deny-all; exclusion permits unlisted future tools and retains blocked reappearances. All mode removes the optional policy property on Apply. Default timeout remains 60000ms; normal untouched defaults are absent and stores are not rewritten at load.

A child-scoped native registration facade filters presentation and rechecks the current policy, pause/closed state and generation immediately before upstream invocation. Old callable references cannot bypass later filtering. It does not replace a root service or remove foreign/sibling registrations. The names-only inventory includes denied advertised names. Incomplete/malformed/oversized registrations fail closed; SDK tools/list fetch/parse errors before any registration can preserve the SDK's previous generation. Admitted descriptions and server instructions still enter the model context. This is **not prompt-injection isolation** or a provider-side permission boundary, and already-dispatched calls cannot be undone.

Live Apply pauses dispatch before disk publication, then requires exact read-back before registration and reopening. Publication or transaction-release uncertainty closes the gate and quarantines that target; explicit successful OFF clears that policy quarantine. No restart/reconnect, credential rewrite, native-config mutation or tool/network invocation occurs for Apply. Opening/checking/searching/Cancel/polling never applies it. The UI retains uncertain state, requires manual Refresh/review and exposes an error-only guarded Confirm OFF action inside Details, including when the saved Switch is already OFF. Failed teardown retains ownership/quarantine.

Configured timeout bounds a tool call through the existing SDK; it is not a configurable initial-handshake timeout, stream deadline or global execution budget. Safe connection categories use fixed allowlists and structured own-data evidence, never arbitrary messages/getters, response prose, stacks or URLs. An admitted POST failure can provide HTTP evidence; optional GET405/DELETE cleanup, broker admission rejection and local cancellation are not diagnoses of the initial MCP connection. Unknown evidence remains generic. A definite reviewed initial connection failure may release the same narrowly proven pending-Save markers as mount-failed; it cannot clear unrelated credential, persistence, cleanup or ambiguous-operation history.

New optional store fields are forward-readable by this candidate; old strict 0.5.5 readers may reject a store once those fields are saved. Code downgrade alone is not a safe rollback/data migration. Preserve the original protected store/key; do not auto-strip fields or migrate credentials.

## Metadata is not a secret channel

Labels, executable/cwd, arguments, URLs and ref names are visible JSON. Bindings contain refs only. URLs reject userinfo/query/fragment; common credential-shaped arguments and hop-by-hop/control headers are refused. Arbitrary positional text/path segments cannot be reliably classified. Never paste credentials into metadata/third-party unencrypted config.

## HTTP credential boundary

Every authorized HTTP mount gets an owned ephemeral **127.0.0.1 port-0** broker. The unchanged official SDK receives only a random 192-bit exact-path capability with empty headers, never vault header values. The capability is not persisted/logged/returned. It is not another GUI/management API.

Upstream is only the validated final URL: HTTPS or explicit loopback HTTP. GET/POST/DELETE use `redirect:'error'`; credentials never follow redirects. Exact Host/path, no query/absolute-form alternate target, Origin/Cookie/browser Fetch fences prevent browser-origin access. Node `sec-fetch-mode` alone is not browser identity. CONNECT/Upgrade are destroyed.

Only MCP protocol headers are copied; incoming auth/cookies/Host/hop-by-hop values are not forwarded. Actual credentials are inserted for the fixed upstream. Responses allowlist headers and omit Set-Cookie/Location. Non-2xx/error bodies get fixed generic diagnostics. Successful MCP/tool bodies remain intact, so a trusted server can still echo a secret.

Bounds: 16KiB request headers, 2MiB request bodies, eight upstream requests, 32 sockets, upload/header idle limits, 60-second upstream response-header deadline. Streaming/backpressure and cancellation are preserved; long-lived successful event streams have no invented total-size/idle guarantee. Broker teardown aborts/destroys only owned work. It is not a general DNS/SSRF firewall or separate-UID isolation.

## Verified save, lifecycle and honest status

Owner/input/revision/ownership/edit-active/capacity/drift guards precede automatic-key IO and mounting. New Save validates metadata/credential refs, requires an owned disposer plus explicit `initialVerified:true` and safe nonnegative verification timestamp. Official mount awaits native readiness with `failOnStartupError:true`; an HTTP 200/active-looking but unverified handle is insufficient. Only verified mounts are added to saved metadata, and successful publication retains them without a second handshake.

Validation failure preserves old saved metadata and does not add a new server. Persistence failure attempts only owned cleanup. Exact old publication state must be proven, or an exact attempted value compensated while holding the writer lock; anything else is explicitly ambiguous rather than assumed rolled back. Rejected cleanup retains ownership and blocks duplicate Save attempts; controller disposal retries retained cleanup. Missing disposer is quarantined/fails closed rather than silently lost. Runtime tool registration can exist during the authorized verification phase before metadata publication; this is not an isolated sandbox or session-private probe.

Editing/deleting active records is refused; toggle OFF first. Overwriting or deleting any existing credential ref still requires all owned mounts stopped, including unused refs. Automatic-mode append of a genuinely fresh ref may preserve other owned mounts, but only with authenticated current vault/ref knowledge and all owner/revision/drift/key/capacity guards. Manual/passphrase writes keep the original all-mounts-stopped requirement. Stop/unmount does not erase the stored configuration. Ordinary stale revisions must not tear down children. Reconnect checks owner/confirmation/revision/bindings before disposal and does not silently restore a failed child. The saved-list Refresh never contacts an MCP server.

For HTTP, broker closure precedes SDK teardown. SDK/Cordis may fulfill disposal after internal cleanup failures; successful local unmount is `unmounted-shutdown-unverified`, not proven remote shutdown/process exit/revocation. Rejected disposal retains `stop-failed`. Legacy Lock clears held access/requests cleanup before reporting a stale/corrupt store, so an error can follow attempted cleanup. Automatic mode does not offer fake durable revocation of its private key.

The serialized queue and writer lock protect local mutations, not independent hosts' live children. Manual TTL queues cleanup/checks expiry but cannot interrupt in-progress SDK work in hard real time. Stdio/SDK may retain credential copies. `activation-verified`/timestamp prove only initial handshake/tool sync, not continuous health. Old compatible unverified starts remain `mounted-status-unavailable`, never fake connected status. Only one console instance should coordinate a profile.

The 0.5.2 compact information/status/verification/reconnect/switch row keeps the same host contracts. Opening, positioning or scrolling its information bubble does not call an MCP or mutate the store. The grey pending symbol is local request progress, not a new backend state or verification result; only the authorized target row may show it. The explicit reconnect-icon click authorizes the existing `RECONNECT THIS SERVER` RPC acknowledgement directly, without an extra modal. It first checks the latest observed revision, exact saved configuration, active state, supported endpoint and absence of pending mutations/Saves. Duplicate clicks are locked out; uncertain/failing replies are not replayed automatically or presented as fresh green verification. Popup geometry is computed before revealing, bounded to the card/viewport and clipping ancestors, with a manual top-layer browser popover and bounded absolute fallback. Native Settings styling is not modified. Qualified status/verification/shutdown limits remain in the accessible information bubble. The native switch remains controlled from backend snapshots; delete confirmations and credential flows are unchanged.

## Explicit persisted Switch and startup authority

Only this plugin's optional strict `enabledIds` metadata records future-start intent: bounded, unique IDs belonging to saved records. Earlier strict readers reject this added metadata rather than ignoring intent; after preferences have been written, do not blindly downgrade just the package or remove flags from the live store. Legacy absence is disabled, not an inferred permission from old mounts. Existing records need an explicit ON once after upgrade. Metadata-only edits cannot keep authorization for a changed/unverified config; successful verified Save stores ON, and explicit OFF publishes disabled intent before owned teardown. Lock, TTL and plugin disposal do not pretend to erase that saved preference. Failed publication/lock release is not assumed success and no unrelated value or retained mount is silently compensated. Uncertain preference publication quarantines that ID until a successful explicit OFF. If already OFF with no live handle, the UI has no same-valued OFF action: safely resolve/confirm any writer-lock condition, then reload only this console's backend plugin context. Refreshing the browser/pane does not clear the controller quarantine; reload never removes a retained writer lock and may clean up/restore other explicitly enabled console records.

`startup()` is an internal lifecycle path, not an RPC/LLM tool and not a forged invocation-owner context. Service registration happens first; remote network readiness does not block console activation. One idempotent bounded sequential pass rechecks the saved enabled flag/config and vault around asynchronous work. Private startup reads refuse an extant writer lock and never remove it as stale. No preference/store/vault/key write, ordinary disabled-store creation, speculative legacy activation or recursive retry is allowed. Only the existing private automatic key may resolve approved refs. Manual passphrases are not persisted/auto-unlocked; locked credential records fail while retaining intent. Startup failure does not cancel healthy siblings; disposal closes the controller and owned late work is cleaned rather than published.

A checked persistent Switch means enabled configuration, not live connectivity. The existing status/verification evidence remains truthful, including failures. A failed enabled record can be explicitly retried via reconnect; an OFF intent with retained teardown failure uses the same icon for explicit retry-stop, not a hidden new connection. Ordinary browser mount/poll/Refresh/info events never authorize connection work. App/profile/plugin startup is the trigger, not automatic launching of DSH at Android device boot. Only one controller/host should coordinate a profile; this is not a cross-process singleton guarantee.

## Logging, filesystem and unsupported boundary

Own RPC/UI diagnostics are fixed/allowlisted. A scoped public logger shadow suppresses own SDK diagnostic arguments without changing the parent logger. The private stdio bridge additionally forwards only stdout and discards the intended child's stderr; configured env keys are decoded only after the bridge Node process starts, so configured NODE_OPTIONS targets the intended child rather than the bridge. The bridge requests cleanup of its owned direct child; it is not descendant/process-group or separate-UID isolation. Successful tool returns, admitted descriptions/server instructions and plugins bypassing these boundaries are not sanitized. Suppression limits diagnosis intentionally.

Private regular files/directories, bounds, symlink refusal, exclusive lock, revisions, temporary fsync/atomic rename/directory fsync protect own publication. Stale locks are not removed automatically. These checks do not isolate root/hostile same-UID ancestor changes or guarantee every-filesystem power-loss recovery.

Only stdio/Streamable HTTP and supplied env/header/Bearer credentials; no OAuth, SSE, credential import/recovery, non-invasive test RPC, broad profile inventory, live-status API or auto-reconnect. External inventory is mounted official namespaces, names only/read-only. No native MCP takeover, engine implementation change or automatic engine-wide restart.
